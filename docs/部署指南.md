## 部署指南：使用 GitHub Actions 自动化部署

XUGOU 系统现在采用单一 Worker 部署方式，前后端集成在一个 Worker 中，并推荐使用 GitHub Actions 实现自动化部署，流程更简单、更安全。

生产发布后的 Readiness、Queue 重放、Worker 回切与 D1 Bookmark 恢复步骤见 [单 Worker 运维与回滚手册](单Worker运维与回滚手册.md)。

### 部署优势

* **自动化**: 每次推送代码到 `main` 分支，即可自动完成构建和部署，无需手动操作。
* **高安全性**: 无需在代码中明文存储数据库 ID 等敏感信息，全部通过 GitHub 的加密 Secrets 功能管理，避免隐私泄露。
* **配置简单**: 只需一次性配置，后续无需再关心部署细节。

### 一键部署步骤

#### 第 1 步：准备 Cloudflare 环境

1.  **创建 D1 数据库**
    * 登录到 Cloudflare 控制台。
    * 访问左侧菜单栏 **Workers 和 Pages** -> **D1**，点击 **“创建数据库”**。
    * 为数据库命名，例如 `xugou_db`。
    * 创建成功后，**记录下数据库的 “数据库 ID” 和 “数据库名称”**，后续步骤会用到。

2.  **创建同 Worker 使用的 Queues**
    * 只需为系统通知和告警异步处理创建一个平台 Queue；Producer 和 Consumer 都属于同一个 `xugou-app` Worker：
      ```bash
      pnpm exec wrangler queues create xugou-jobs
      ```
    * Queue 是 Worker Binding，不是额外服务或部署单元。已有同名 Queue 时保留现有资源与积压消息。

3. **创建私有 Raw Sample R2 Bucket**
    * 原始 Agent/Monitor 样本在 D1 清理前必须先进入带 SHA-256/Size/ETag 证据的 R2 归档：
      ```bash
      pnpm exec wrangler r2 bucket create xugou-raw-sample-archive
      pnpm exec wrangler r2 bucket info xugou-raw-sample-archive
      ```
    * 保持 Bucket 私有，不开启公开域名或自动删除 Lifecycle。R2 只是同一 Worker 的存储 Binding，不增加 Worker 或微服务。

4.  **创建 API 令牌**
    * 在 Cloudflare 控制台，点击右上角的用户图标，进入 **“我的个人资料”** -> **“API 令牌”**。
    * 点击 **“创建令牌”**，然后选择 **“编辑 Cloudflare Workers”** 这个模板。
    * 保持默认的权限配置不变，点击 **“继续以显示摘要”** -> **“创建令牌”**。
    * **立即复制生成的 API 令牌**，这个令牌只会显示一次。

5. **配置 Worker Secrets**
    * 以下值由同一个 `xugou-app` Worker 使用，不写入仓库或 `wrangler.toml`：
      ```bash
      openssl rand -base64 48 | pnpm exec wrangler secret put SESSION_HMAC_SECRET
      openssl rand -base64 48 | pnpm exec wrangler secret put AGENT_TOKEN_PEPPER
      openssl rand -base64 32 | pnpm exec wrangler secret put NOTIFICATION_KEK
      openssl rand -base64 24 | pnpm exec wrangler secret put ADMIN_INITIAL_PASSWORD
      openssl rand -hex 32 | pnpm exec wrangler secret put RELEASE_READINESS_TOKEN
      ```
    * `ADMIN_INITIAL_PASSWORD` 只在全新数据库创建固定 `admin` 账号时读取，至少 12 位；已有数据库继续使用原密码。
    * Session HMAC、Agent Pepper、Notification KEK 与 Release Readiness Token 上线后需保持稳定并纳入受控备份；直接替换会使对应摘要、密文或发布门禁失配。
    * `RELEASE_READINESS_TOKEN` 的同一个值还要写入 GitHub Actions Secret；不要分别生成两个值。
    * 前端静态资源默认由同一 Worker 提供，因此管理 API 默认只接受同源浏览器请求。只有管理前端确实部署在另一个可信 Origin 时，才在 `[vars]` 中配置逗号分隔的完整地址，例如 `ALLOWED_ORIGINS = "https://console.example.com"`；凭据化 CORS 不接受 `*`。

6. **升级前执行数据预检**
    * 先把远程 D1 导出到受保护的本地临时文件，再运行只读预检：
      ```bash
      mkdir -p .backups
      pnpm exec wrangler d1 export D1_DATABASE_NAME --remote --output=.backups/xugou-preflight.sql
      pnpm --dir backend migration:preflight -- --sql-export .backups/xugou-preflight.sql --allow-empty
      pnpm exec wrangler d1 migrations apply D1_DATABASE_NAME --remote
      ```
    * JSON 报告中的 `readyForExpand` 必须为 `true`，以允许继续部署。
    * 预检覆盖完整性、外键、单管理员、非法通知 JSON、孤立状态页关联、Credential/Notification 回填缺口和旧历史表清单，报告不输出 Token 或 Secret 原文。

#### 第 2 步：Fork 项目并配置 GitHub Secrets

1.  **Fork 仓库**
    * 访问项目主页 [https://github.com/zaunist/xugou](https://github.com/zaunist/xugou) 并点击右上角的 **Fork** 按钮，将项目复制到你自己的 GitHub 账户下。

2.  **修改 `wrangler.toml` 文件（如果尚未修改）**
    * 确保你 Fork 的仓库根目录下的 `wrangler.toml` 文件中的 `d1_databases` 部分使用了占位符。**本项目已为您配置好，无需修改**。正确的配置如下：
        ```toml
        [[d1_databases]]
        binding = "DB"
        database_name = "${D1_DATABASE_NAME}" # 使用占位符
        database_id = "${D1_DATABASE_ID}"   # 使用占位符
        migrations_table = "migrations"       # 桥接旧运行时迁移账本
        migrations_dir = "backend/drizzle"

        [[r2_buckets]]
        binding = "RAW_SAMPLE_ARCHIVE"
        bucket_name = "xugou-raw-sample-archive"

        [[queues.producers]]
        binding = "XUGOU_JOBS"
        queue = "xugou-jobs"

        [[queues.consumers]]
        queue = "xugou-jobs"
        max_batch_size = 10
        max_batch_timeout = 5
        max_retries = 5
        max_retries = 5
        ```

3.  **配置 GitHub Secrets**
    * 进入你 Fork 后的 GitHub 仓库，点击 **Settings** -> **Secrets and variables** -> **Actions**。
    * 点击 **New repository secret** 按钮，依次添加以下 **6 个**部署凭据：
        * `XUGOU_CF_API_TOKEN`: 粘贴仅授予 XUGOU 所在账号的 Workers Scripts、D1、R2、Queues 编辑权限的 Cloudflare API 令牌。
        * `XUGOU_CF_ACCOUNT_ID`: XUGOU 所在 Cloudflare **账户 ID**。
        * `XUGOU_D1_DATABASE_ID`: 你在**第 1 步**中创建的 D1 数据库 **ID**。
        * `XUGOU_D1_DATABASE_NAME`: 你在**第 1 步**中创建的 D1 数据库**名称**。
        * `RELEASE_READINESS_URL`: Worker 的完整 HTTPS 根地址，不包含 API 路径和末尾斜杠。
        * `RELEASE_READINESS_TOKEN`: 与 Worker Secret 完全相同的发布门禁 Token。
    * `wrangler login` 只为当前电脑建立登录态；GitHub Runner 仍使用上述 `XUGOU_CF_API_TOKEN`，两者相互独立。

#### 第 3 步：触发部署

配置完成后，部署将自动进行！

* **自动部署**: 每当你向仓库的 `main` 分支推送代码时，GitHub Action 会依次执行统一质量门禁、升级前 Bookmark/Export/Preflight、Migration、升级后 Postflight/Manifest、单 Worker 发布和受保护 Readiness。
* **手动部署**: 进入仓库的 **Actions** 标签页，点击左侧的 **Deploy to Cloudflare**，再点击 **Run workflow**。手动触发默认使用 `main` 当前提交。
* 功能分支推送只保存候选代码，不触发生产部署；合并或直接推送到 `main` 才触发自动生产流程。
* 首次 Expand 升级的 Backfill 由每分钟 Cron 幂等推进，Stage 5 最长轮询 75 分钟；后续无待回填数据的普通发布通常首轮通过。
* Stage 1/3 的全量 D1 Export 会显示短暂维护窗口提示；Queue Consumer 在此期间保留消息级指数退避。发布完成时还需确认 Stage 5 的 Job/Outbox Lag 均低于门槛。

### 部署完成

普通发布耗时主要由统一质量门禁决定；首次历史数据升级还包含 Backfill 等待时间。Actions 中 **Stage 5 - Protected release readiness** 通过后，才代表本次发布完成。

* **访问地址**: `https://<你的项目名>.<你的workers.dev子域>.workers.dev`
* 项目名在 `wrangler.toml` 文件中定义 (默认为 `xugou-app`)。
* 你也可以在 Cloudflare 控制台为你的 Worker 绑定自定义域名。
