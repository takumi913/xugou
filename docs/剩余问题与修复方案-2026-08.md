## 1. 重构边界与验收原则

- 部署形态保持 **一个 Cloudflare Worker**：Hono API、静态前端、Cron、Queue Consumer 与 Durable Object 由同一 Worker Bundle 发布；D1、R2、Queue、Durable Object 仅作为平台 Binding。
- 不引入 Docker，也不以容器作为开发、测试、部署或回滚前提。
- 系统保持单实例、单管理员模型，不恢复租户、组织、成员或租户隔离概念。
- 数据结构变更统一采用 **Expand → Backfill → Verify → Contract**：先扩展兼容结构，再幂等回填并核对，最后清理旧结构。
- 所有 D1 变更均需保留迁移账本、升级前导出和 Bookmark；旧数据在守恒校验通过前不删除、不覆盖。
- 对外契约优先保持兼容。确需替换时，旧接口或旧格式保留一个明确的静默窗口，并通过可观测指标确认已无调用。

## 4. P0：公开数据边界

### PUB-01：字符串化指标绕过敏感键检查

**证据**

- `backend/src/modules/agents/http/schemas.ts` 的 `agentV4ReportSchema` 允许 `disks[]`、`network[]` 使用任意键对象；
- `backend/src/modules/status/domain/public-contract.ts` 的 `parsePublicStatusSnapshot()` 只检查解析后对象的键；
- `backend/src/modules/status/persistence/D1StatusRepository.ts` 把部分指标保存为二次编码的 JSON 字符串。

因此 `disk_metrics='[{"token":"..."}]'` 的内层键不会参与当前递归检查。

**修复方案**

1. 为磁盘、网卡和地址数据定义严格 Zod Schema，只接收业务字段白名单，并设置合理的数组长度和字符串长度上限。
2. 新建结构化 `PublicAgentMetrics` DTO；公开投影中不再保存 JSON 字符串。
3. Publication Builder 读取旧数据时先解析旧字符串，按白名单投影，再执行递归敏感键检查。
4. 对解析失败的单条旧指标做隔离记录，不把原始值写入日志或公开响应。
5. 增加 `token`、`api_key`、`access_token`、`secret` 位于对象、数组和字符串化 JSON 内的回归用例。

**旧数据兼容**

- 读取端同时支持旧字符串和新结构化字段；
- Backfill 分页生成新投影，不原地修改旧样本；
- 校验新旧记录数、Agent 覆盖率与投影失败数后，再停止旧格式读取。

**完成标准**

- 任意层级敏感键均使 Publication 构建失败并产生脱敏告警；
- 公开 API 与持久化 Publication 中不存在二次编码的指标对象；
- 旧样本回放测试和新 v4 上报测试均通过。

### PUB-02：公开 GET 触发 Builder 和 D1 写入

**证据**

- `backend/src/modules/status/application/StatusUseCases.ts` 的 `getPublicData()` 在活动 Publication 缺失时调用 `buildPublicData()`；
- Builder 会进入 `ensureConfig()` 和多表查询路径。

**修复方案**

1. 迁移完成或 Cron 启动时幂等写入首个 `status.publication.rebuild` Outbox 事件。
2. Queue Consumer 构建不可变 Publication，校验成功后再切换活动指针。
3. 匿名 GET 只读取活动指针；指针缺失时返回统一 Problem Details、`Retry-After` 和可观测错误码。
4. 将 Seed、Backfill、Builder 从所有公开请求路径移出。

**旧数据兼容**

- 首次启动读取现有 `status_page_config` 和关联表生成首份 Publication；
- 构建失败时保留上一活动版本，不移动指针；
- 已有状态页配置和 slug 不变化。

**完成标准**

- 公开 GET 在空指针场景不产生 D1 写入；
- Builder 只由迁移、Cron 或 Queue 触发；
- Publication 指针切换具备失败回滚测试。

### PUB-03：公开历史指标直读运行表

**证据**

- `/api/v2/status/public/agents/:id/metrics` 经 `D1StatusRepository` 直接读取 Rollup、Sample 或旧 History；
- 该路径未复用 v1 的 Cache API、ETag 和 `PUBLIC_METRICS_CACHE_TTL_SECONDS`。

**修复方案**

1. 建立有界、不可变的 `PublicMetricPublication`，与主状态 Publication 共享版本或显式关联版本。
2. Builder 只投影允许公开的 Agent、时间范围、粒度和字段。
3. 公开路由只读活动 Publication，恢复 ETag、条件请求和 Cache API。
4. 禁止公开路由回退到 Sample、Rollup 或旧 History 表。

**旧数据兼容**

- 初次 Backfill 从现有 Rollup 生成公开历史，不复制原始敏感样本；
- 旧 v1 响应格式在静默窗口内保持字段兼容；
- 新旧响应按 Agent、时间桶和数值误差阈值做影子对比。

**完成标准**

- 公开路由代码不再依赖运行时样本 Repository；
- ETag 命中返回 304，缓存 TTL 生效；
- 隐藏 Agent 和未发布时间桶在所有公开路径均不可见。

### REL-01：Agent 发布对象非原子

**证据**

- `.github/workflows/build.yml` 逐个覆盖 R2 `latest/` 下的 Manifest、签名和二进制；
- `workflow_dispatch` 的 Build 与 Upload Job 分别计算版本，分支触发时可能产生不同版本值。

**修复方案**

1. Build Job 只计算一次合法 SemVer / 预发布版本，通过 Job Output 传给后续步骤。
2. 上传到不可变 Key：`releases/<version>/<artifact>`。
3. 先上传二进制和签名，逐个校验 SHA-256、Size、ETag，再上传 Manifest。
4. 最后更新一个小型、带签名的 `channels/stable.json` 或 `channels/dev.json` 指针。
5. Agent 先验证指针签名，再读取不可变 Manifest 和 Artifact；保留旧 `latest/` 一个静默窗口。

**旧数据兼容**

- 旧 Agent 继续读取 `latest/`；发布流程在窗口期同时维护旧路径和新指针；
- 监控旧路径访问量归零后停止更新，历史对象延迟清理。

**完成标准**

- 任一步骤失败都不会改变活动指针；
- 手工触发与 Tag 触发使用同一个版本值；
- 客户端在并发发布测试中只看到完整旧版或完整新版。

### SCH-01：Monitor 调度吞吐受单批次限制

**证据**

- `backend/src/modules/monitors/queue/MonitorScheduler.ts` 每次 Cron 只查询一个 `LIMIT` 批次；
- 默认每分钟 10 个、监控周期 5 分钟时，稳态及时调度容量约为 50 个；
- `MONITOR_CHECK_CONCURRENCY` 已配置但未参与执行。

**修复方案**

1. 使用 `(next_check_at, id)` Keyset 分页，Cron 在明确的时间预算内连续入队。
2. 每批提交后更新游标；重复触发依赖 Job Ledger 幂等键去重。
3. Readiness 增加 `oldest_due_at`、scheduler lag、due count 和 enqueue rate。
4. Queue Consumer 先依赖平台并发；有压测数据后再引入有界批内并发。
5. 对 50、500、5000 个 Monitor 做吞吐、重试和超时基准。

**旧数据兼容**

- 继续使用现有 Monitor、Job Ledger 和 Queue 消息格式；
- 新游标只影响扫描策略，不重写 Monitor 数据。

**完成标准**

- 最大规模基准下 scheduler lag 保持在约定 SLO 内；
- Cron 接近预算时可续跑，不丢失、不过量重复调度；
- Readiness 能反映尚未生成 Job Ledger 的逾期 Monitor。

### MIG-01：部署缺少迁移后数据复检

**修复方案**

1. 迁移前导出远程 D1 并运行 Preflight。
2. 应用 Migration 后再次导出，运行完整性、外键、数据守恒和 Manifest delta 检查。
3. Worker 发布后，以专用发布凭据调用 Release Readiness。
4. 任一阶段失败即停止后续发布，保留导出、Bookmark、Migration ID 和日志证据。
5. 将回切入口与 [`单Worker运维与回滚手册.md`](单Worker运维与回滚手册.md) 对齐。

**完成标准**

- `.github/workflows/deploy.yml` 包含 preflight、apply、postflight、deploy、readiness 五阶段；
- 发布产物可关联 Git SHA、D1 Bookmark、迁移清单和 Readiness 结果；
- 故障演练证明可按手册恢复。
