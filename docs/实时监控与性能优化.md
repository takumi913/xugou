# 实时监控与性能优化

本文档记录 XUGOU 实时监控链路（WebSocket）、D1 存储优化与 agent 配置下发协议的设计要点，参照 CF-Server-Monitor 的成熟方案在 Cloudflare Workers + D1 架构下落地。

## 一、WebSocket 实时链路

### 架构

```
Go Agent --(HTTP 批量上报)--> Worker /api/agents/status
                                  │ 落库成功后
                                  ▼
                    MetricsBroadcaster (Durable Object, idFromName('global'))
                                  │ /batch-push 批量广播
                                  ▼
              浏览器 <--(WS 推送 batchUpdate)-- /api/ws
```

- **单实例 DO 广播中心**：`backend/src/durable/MetricsBroadcaster.ts`。所有前端 WebSocket 连接挂在同一个 DO 上；Worker 在指标落库成功后调用 DO 的 `/batch-push` 接口批量推送。
- **Hibernation API**：使用 DO WebSocket Hibernation，闲置时休眠不计费；`setWebSocketAutoResponse` 自动应答 `ping`/`pong` 心跳，无需唤醒 DO。
- **订阅鉴权**：`GET /api/ws` 在 Worker 侧完成 JWT 校验（支持 `?token=` 查询参数或 `Sec-WebSocket-Protocol` 子协议携带），校验通过后才转发到 DO。非 admin 用户的可见 agent 列表通过 `X-Allowed-Agent-Ids` 传入 DO，越权订阅的数据不会下发。
- **订阅粒度**：`subscribe=all` 订阅全部（受权限约束），或 `subscribe=<id,id,...>` 只订阅指定 agent（上限 500 个）。
- **批量推送**：agent 每 5s 上报一批（内含多条 2s 采样），DO 收到后按订阅范围过滤，一次 `batchUpdate` 消息携带整批 samples 下发，前端按时间戳逐条渲染出秒级曲线。
- **最近数据回放**：DO 内存保留每个 agent 最近一包上报（TTL 5 分钟、上限 1000 agent、每 agent 至多 300 条采样）。新页面建立连接后立即收到回放数据，无需等下一个上报周期即可渲染。
- **前端**：`liveSocket` 单例 + hooks 封装，断线自动重连，仪表盘显示 `● live` 指示。

## 二、D1 存储优化

### 分区整型主键（免二级索引）

`agent_metrics_history` 历史表主键为运行时构造的整型：

```
id = history_partition_id * 10^13 + YYMMDDHHmmss（UTC 数字拼接）
```

- 每个 agent 分配一个 `history_partition_id`（1~900，受 JS 安全整数上限约束）。
- "某机某时段" 的查询变成主键 `BETWEEN startId AND endId` 范围扫描，**不需要任何二级索引**——索引写放大归零（每写一行只写主键 B-tree，无附加索引维护成本）。
- 工具函数见 `backend/src/utils/historyId.ts`。

### 周表轮换（免行级删除）

`backend/src/jobs/rotation-task.ts`，每周日 UTC 00:00 由 cron 触发：

1. `DROP TABLE agent_metrics_history_old`（丢弃上上周数据）；
2. `agent_metrics_history` RENAME 为 `agent_metrics_history_old`；
3. 重建空的 `agent_metrics_history` 主表。

历史数据清理由按行 `DELETE` 改为整表 `RENAME + DROP`，**行级删除计费清零**（D1 的 DROP TABLE 成本与行数无关）。轮换保护窗口（周日 0:00–0:05 UTC）内跳过 agent 离线检测防止误报；主表 + old 表合计保留约 1~2 周数据，**7 天历史随时可查**。

### SQL 层时间桶降采样

`backend/src/repositories/agent.ts` 中历史查询：

- 按 `hours` 白名单（1/6/12/24/168）确定时间桶大小，SQL 内 `GROUP BY strftime('%s',timestamp)/intervalSec` 聚合；
- 数值列取桶内 AVG（连接数/进程数取 MAX），`MAX(id)` 桶代表行提供裸列值；
- **单次查询固定返回 ≤160 行**，前端渲染压力与查询时间窗大小解耦；
- 时间窗跨轮换边界时自动 `UNION ALL` old 表，old 表被并发轮换删除时降级为只查主表。

### isolate 内存缓存

`backend/src/utils/memCache.ts` 提供轻量 TTL 缓存，agent 列表、最新指标批查、历史查询结果均有独立缓存与 TTL；表轮换后主动清空相关缓存避免读到旧数据。热点读（仪表盘/状态页轮询）大部分命中内存，不再重复打到 D1。

### 量化收益小结

| 优化项 | 收益 |
| --- | --- |
| 分区整型主键 | 历史表零二级索引，索引写放大归零 |
| 周表轮换 | 行级 DELETE 计费清零，清理耗时 O(1) |
| SQL 降采样 | 单次历史查询响应固定 ≤160 行 |
| 主表+old 表双表 | 7 天（168h）历史可查 |
| memCache | 热点读大幅减少 D1 行读计费 |

## 三、Agent 配置下发协议

采集/上报间隔可在网页端修改并远程下发给 agent，协议基于上报请求的 MD5 协商：

- **规范化配置串**：`collect_interval=<秒>&report_interval=<秒>&schema_version=2`，键按固定顺序拼接，MD5 即配置指纹。
- **协商流程**：agent 每次批量上报附带头 `X-Agent-Config-Md5`（本地配置串 MD5）与 `X-Agent-Config-Schema`（协议版本）；服务端比较自身配置的 MD5，一致则响应不带配置（无变化），不一致则在响应中下发完整规范配置串并附上服务端 MD5。
- **严格解析**：agent 侧 `ParseRemoteConfig` 白名单校验——仅接受上述三个键，拒绝未知键、重复键、空值、非整数、越界值（`report_interval` 必须 ≥ `collect_interval`）、百分号编码与前后空白，防止服务端被攻破后借配置通道注入命令或 URL。
- **原子持久化**：新配置校验通过后写入本地配置文件（临时文件 + rename 原子替换），下个采集/上报周期即生效，无需重启进程。
