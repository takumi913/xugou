## 一、必须立刻修的安全问题

### S1. 任意登录用户可重置任意账号（含 admin）的密码 —— 已核实

`backend/src/api/users.ts:124-145` 的改密路由**完全没有读取 `jwtPayload`**，也没把调用者身份传给 service；
`backend/src/services/UserService.ts:272-312` 同样不校验调用者，且 `currentPassword` 仅在「客户端主动提供时」才验证：

```ts
// UserService.ts:291
if (passwordData.currentPassword) {   // 不传就完全跳过校验
  const isPasswordValid = await compare(passwordData.currentPassword, user.password);
```

`api/schemas.ts:314` 中 `currentPassword: z.string().optional()` 坐实了这一点。

**利用方式**：任意 role=`user` 的账号发送 `POST /api/users/1/change-password {"newPassword":"xxxxxx"}` 即可接管 admin。

对比证据：同文件 `users.put("/:id")` 和 `users.delete("/:id")` 都正确取了 `payload.id / payload.role`，唯独改密漏掉——是疏漏而非设计。

**修法**：路由取 `jwtPayload` 传入 service；非 admin 只能改自己且必须提供 `currentPassword`；admin 改他人时才允许免旧密码。

### S2. 通知历史无租户隔离，可一次性导出全站 —— 已核实

`backend/src/repositories/notification.ts:397-447` 的 `getNotificationHistory` **签名里根本没有 userId**，查询 `notificationHistory` 全表无任何归属条件；`api/notifications.ts:681-720` 也不传。
`db/schema.ts:528-551` 的 `notification_history` 表本身没有 `user_id/created_by` 列——结构上就无法隔离。

`limit` 无上限（`api/notifications.ts:688` 直接 `parseInt`），`GET /api/notifications/history?limit=999999` 可导出所有用户的通知内容，其中 `content` 含各租户的监控 URL、主机名等。

**修法**：给表加 `created_by` 列并回填（可经 `channel_id → notification_channels.created_by` 推导），查询强制按调用者过滤，`limit` 设上限。

### S3. 公开状态页泄露监控项全部字段，包括请求头里的凭据 —— 已核实

`backend/src/services/StatusService.ts:350-356` 把监控行整行透传：

```ts
const monitors = (monitorRows as any[])
  .filter((monitor) => selectedMonitorIdSet.has(monitor.id))
  .map((monitor) => ({ ...monitor, dailyStats, history }));
```

`monitorRows` 来自 `repositories.getMonitorsByIds`（`repositories/monitor.ts:160-172`）的 `db.select()` 全列，含 `url / method / headers / body / created_by / expected_status`。
而 `/api/status/public/:userId/data` 是无鉴权端点（`middlewares/auth.ts:43` 的 `isPublicStatusRoute` 放行）。

**危害**：监控项的自定义请求头常含 `Authorization`、API Key（前端 EditMonitor 就是让用户填这个的），现在对全互联网公开。

对比证据：同文件 `toPublicAgent`（`StatusService.ts:47-64`）对 agent 做了极严格的字段白名单，还写了注释强调 `ip_addresses`/`geo_*` 绝不外泄——monitor 侧没有任何对应投影，是不对称的遗漏。

**修法**：照 `toPublicAgent` 写一个 `toPublicMonitor`，只输出 `id/name/status/type` 等展示必需字段。

### S4. 源码中硬编码真实 Telegram Bot Token —— 已核实

`backend/src/db/seed.ts:126` 与 `backend/src/services/NotificationService.ts:1613`：

```
'{"botToken": "8538953065:AAG51lJ31MNLWe3na5wai4SBRiZ8T-sOC3c", "chatId": "1111111111"}'
```

凭据已随仓库公开，且每注册一个新用户就插入一条使用该 token 的**启用状态**渠道。

**修法**：立刻在 BotFather 吊销该 token；默认渠道改为不预置凭据的禁用模板；清理已写入的存量行。

### S5. JWT 密钥失败开放 + 绑定部署版本 ID —— 已核实

`backend/src/utils/jwt.ts:15-30` 在拿不到 `CF_VERSION_METADATA` 时回退到 `constants.ts:18` 的公开硬编码字符串 `"your-secret-key-change-in-production"`——是**失败开放**而非失败关闭，任何人都能用仓库里的公开字符串签发合法 admin JWT。

同时该函数注释声称「优先从环境变量中获取 JWT_SECRET」，但代码**从未读过 `env.JWT_SECRET`**，正确修法根本没实现。

密钥 = 部署版本 ID 带来的连锁问题：
- 每次 push main 自动部署 → 全站用户强制登出；
- agent 注册令牌同用此密钥签发（`jwt.ts:39-77`），网页生成 token 后若发生过一次部署，agent 注册必然报「令牌无效」；
- Docker 部署下 wrangler dev 的 version id 随容器重启变化 → 每次重启全员登出。

**修法**：读 `env.JWT_SECRET`（wrangler secret），缺失时直接抛错拒绝服务，删掉 `DEFAULT_SECRET`。

### S6. 跨租户删除：可清空他人渠道的通知历史

`backend/src/repositories/notification.ts:82-129` 先删历史、后校验归属：

```ts
await db.delete(notificationHistory).where(eq(notificationHistory.channel_id, id)); // 无 userId 约束
...
await db.delete(notificationChannels)
  .where(and(eq(...id), eq(notificationChannels.created_by, userId)));  // 只有这里校验
```

传入他人的 `channel_id`，对方历史被清空，接口仍返回 `true`（第 124 行「假设没有错误就是成功」）。

### S7. Agent 注册令牌：任意用户可签发、永不过期、注册后归 admin

- `api/agents.ts:194-206` 无角色校验，普通用户即可签发；
- `utils/jwt.ts:122-127` 解析出 timestamp 后**从不校验过期**，无一次性/吊销机制；
- `services/AgentService.ts:616-628` 一律用 `getAdminUserId()` 作 `created_by`——普通用户签发的 agent 归属 admin，与已修复的 S-001 多租户边界语义冲突；
- `repositories/users.ts:166` 按 `username = 'admin'` 字符串查管理员，改掉 admin 用户名则所有注册失败。`docs/常见问题.md:32-36` 把这个 bug 当作「解决方案」记录了下来，代码至今未按 `role='admin'` 修正。

### S8. 探针自升级链路无完整性校验（供应链风险）

`agent/pkg/selfmgmt/manage.go:52-53` 注释自认「分发端未提供 sha256 校验文件」，`ValidateBinaryFile` 只校验 4 字节魔数；`manage.go:98-108` 在替换决策**之前**就直接执行刚下载的二进制取版本号；下载地址可被 `XUGOU_UPDATE_URL` 环境变量覆盖为任意 http。
根因在分发侧：`.github/workflows/build.yml:122-207` 只上传 `latest/` 通道、无版本化目录、**不产出 sha256**。

多数探针以 root 跑 systemd（`install-agent.sh:250`），R2 或分发域被控 = 所有开启 auto_update 的主机 RCE。这与 `docs/实时监控与性能优化.md:80` 宣称的安全模型直接矛盾。

### S9. jwtMiddleware 用 `endsWith` 模糊放行

`middlewares/auth.ts:23-31` 中 `/register`、`/login` 是**后缀匹配**。注释里已承认因此出过一次事故（才把 `/status` 改成精确匹配），但另两条仍是后缀匹配——未来任何新增的 `POST /api/xxx/login` 类路径会自动变成匿名端点。应改为精确路径白名单常量表。

## 二、逻辑错误（功能不按预期工作）

### L1. 监控自定义请求头：编辑过一次就永久失效

三层重复解析/编码互相打架：

| 层 | 行为 |
|---|---|
| `api/schemas.ts:33` | `headers` 允许 string 或 object 两种形态 |
| `services/MonitorService.ts:206` | 非 string 则 `JSON.stringify` |
| `repositories/monitor.ts:450` | **再 stringify 一次** |
| `repositories/monitor.ts:64-76` | 读取时又 parse 成对象 |
| `services/MonitorService.ts:54-68` | 只在 `typeof === "string"` 时才构造 Headers |

实际结果：

- POST 创建的监控 → 双重编码，检查时**恰好**能发送（两个 bug 抵消）；
- PUT 编辑过的监控 → 单重编码，检查时 `headers` 为空对象，**自定义请求头被静默丢弃**。

前端被迫写 `typeof monitor.headers === "string" ? JSON.parse(...)` 兼容（`EditMonitor.tsx:86-89`、`MonitorDetail.tsx:201`），这就是症状证据。

**修法**：编解码只在 repository 一层做，schema 只接受 object。

### L2. 更新通知渠道时只改名字，会把渠道静默禁用 —— 已核实

`repositories/notification.ts:72`：

```ts
enabled: channel.enabled ? 1 : 0,   // undefined ? 1 : 0 === 0
```

drizzle 会过滤 `undefined` 的键，但三元运算后永远是确定的 `0`。`PUT /channels/:id {"name":"新名字"}` → `enabled=0`，用户从此收不到通知且无任何提示。

相邻的 `updateNotificationTemplate:185-209` 用的是正确的 `if (x !== undefined)` 模式——两个函数写法不一致，证明是疏漏。

### L3. 通知历史筛选恒返回空、total 恒为 0 —— 已核实

`repositories/notification.ts:404-441` 是裸 SQL 时代的残留，被改成 drizzle 后没改干净：

```ts
let whereParams = [];                      // 声明后从未使用
const whereClause = `WHERE ${conditions.join(" AND ")}`;   // 拼出字符串
const countResult = await db.select({count: count()}).from(...).where(whereClause);  // 给 drizzle 传字符串
const total = countResult?.count || 0;     // countResult 是数组，.count 永远 undefined
```

两个 bug：字符串被当绑定参数渲染成 `WHERE ?`，SQLite 求值为假 → **带任何筛选条件必返回 0 行**；`total` 恒为 0。

之所以没被发现，是因为 `db` 被声明成 `any`（见 A1），TypeScript 查不出 `.where(string)` 和 `.count`。

### L4. `CURRENT_TIMESTAMP` 被当字符串字面量写库 —— 已核实

`db/schema.ts:69,235,343,344,466,467,488,489,543` 用 `text(...).default("CURRENT_TIMESTAMP")`，生成的 DDL 是带引号的字面量：

```sql
-- generated-migrations.ts:109
`created_at` text DEFAULT 'CURRENT_TIMESTAMP',
```

凡是不显式传时间的 insert（`createNotificationChannel`、`createNotificationTemplate`、`createStatusPageConfig`）都会写入字面文本 `"CURRENT_TIMESTAMP"`，按时间排序/展示全是坏的。应改用 `sql\`CURRENT_TIMESTAMP\`` 或应用层显式赋值。

### L5. 状态页历史数据截断方向错误，丢的是最新数据

`repositories/monitor.ts:229-243`：`orderBy(asc(bucket_start)).limit(10000)`，且 LIMIT 跨所有 monitor 生效。24h × 5min 桶 = 288 行/监控，**超过 35 个监控项**就会截断——因为是升序，被截掉的是最近的桶，状态页显示成「最近几小时没数据」。同函数的 fallback 分支用 `desc + reverse()`（正确），两条路径行为不一致。

### L6. 监控检查缺少抢占租约，存在重复检查

`repositories/monitor.ts:49-77` 先 SELECT 出到期监控，`services/MonitorService.ts:127` 在 **HTTP 请求完成之后**才更新 `next_check_at`。竞态窗口 = 整个请求耗时（最长 timeout）。cron 每分钟触发叠加手动检查时，同一监控被查两次 → 重复通知、rollup 计数翻倍。应先原子 claim（`UPDATE ... WHERE next_check_at <= now RETURNING`）。

### L7. `updateAgent` 全行覆盖导致并发上报丢失更新

`repositories/agent.ts:338-357` 把内存整行写回。两个并发上报（或上报 + 管理端 PUT）读同一版本再全量写回 → 后写覆盖先写，`status`、`last_seen_at`、`next_offline_at` 会被回退成陈旧值。

### L8. 定时任务用「精确分钟相等」触发，漏一分钟跳过整周期

`jobs/index.ts:43`（`hour===0 && minute===30`）、`rotation-task.ts:48-52`、`expiry-task.ts:32-34` 都要求分钟精确匹配。Cloudflare cron 不保证每分钟必达——漏掉周日 00:00 那一分钟，`agent_metrics_history` 整周不轮换、无限增长。应改为持久化 `last_run_at` + 「距上次超过 N 就跑」。

### L9. `timeout` 单位与校验上限不匹配

`api/schemas.ts:31` 上限 `120000`（按毫秒设），`MonitorService.ts:48-51` 却按秒用（`* 1000`）。用户填 120000 → 33 小时的 abort 定时器，超时保护形同虚设。

### L10. 上线通知是裸 Promise，可能被 Workers 中止

`AgentService.ts:714-722` 用 `.catch()` 而非 `waitUntil`，且 env 传的是 `{}`。同函数里 `queueMetricsBroadcast` 是正确用 `executionCtx.waitUntil` 的——不一致。

### L11. 探针 `--interval` 参数是死代码 —— 已核实

`cmd/agent/root.go:35-37` 给三个 flag 都设了非零默认值（interval=60、collect-interval=60、report-interval=300）并 BindPFlag 到 viper；
`cmd/agent/start.go:42-53` 的兼容回退却依赖 `<= 0` 判断：

```go
if config.CollectInterval <= 0 {     // 永假：flag 默认就是 60
    config.CollectInterval = config.Interval
}
```

viper 对已绑定 flag 永远返回默认值，条件恒假。用户传 `--interval 30` 时 `config.Interval` 确实变成 30，但**这个值不会传递给任何实际使用的间隔**（`grep` 确认 `config.Interval` 只在 start.go:34/42/43 出现）。

连锁影响：`install-agent.sh:245` 生成的 systemd 单元 `ExecStart=... --interval "${AGENT_INTERVAL}"` 完全无效，安装脚本的 `--interval` 选项是摆设。

### L12. 服务端删除 agent 后，探针永久失败且不会重注册

`agent/pkg/reporter/reporter.go:93-99` 的 `Registered` 一旦置 true 进程内永不重置。服务端找不到 token 时返 500（`api/agents.ts:344-352`），探针只能每周期重试同样的失败，直到进程重启。无 4xx/404 触发重注册的分支，无退避。

### L13. 上报失败恢复路径脆弱

`reporter.go:57-59` 的 10s 硬超时压过了 `start.go:142` 的 `max(ReportInterval,15)s` ctx 超时（两处超时语义矛盾）。失败积累到 300 条样本后，每条 Sample 内嵌完整磁盘/网卡数组，payload 可达数百 KB，**无 gzip、无分块、无指数退避**——慢链路上永久失败循环。

### L14. 前端：列表行用随机 key，每次渲染整表重建 —— 已核实

`frontend/src/pages/monitors/MonitorsList.tsx:359`：

```tsx
<TableRow key={`${monitor.id}-${Math.random()}`}>
```

每次 render 全部行 remount，彻底破坏 reconciliation，配合 60s 轮询持续全量重建 DOM。

### L15. 前端：轮询把 loading 置回 true，整页每 60s 闪一次加载页

`MonitorsList.tsx:82/144/258`、`AgentsList.tsx:73/97/350`、`MonitorDetail.tsx:55/90/126`、`AgentDetail.tsx:122/161/288` 都是「fetch 先 setLoading(true)」+「渲染层 `if (loading) return <PageLoading/>`」，导致每 60s 整页退化为加载页，滚动位置和展开状态全丢。

`Dashboard.tsx:26-27,56-59` 和 `StatusPage.tsx:34-35,56-59` 已用 `initialLoadDone` ref 修好了这个问题，但修复没有回移植到另外 4 个页面——同一 bug 修一半。

### L16. 前端：MonitorsList 一次轮询失败就永久卡在错误页 —— 已核实

`MonitorsList.tsx:81-142` 的 `fetchData` 只 `setError(...)` 从不 `setError(null)`，而渲染层 `if (error) return ...`（:263）优先于正常内容。任何一次网络抖动后，即使后续轮询全部成功，页面也永远停在错误页，只能刷新浏览器。

对照 `AgentsList.tsx:74` 有 `setError(null)`——两个复制粘贴出来的页面在关键行为上已漂移。

### L17. 前端：StatusPageConfig 保存无异常处理

`StatusPageConfig.tsx:138-163` 无 try/catch（axios 抛错则按钮永久卡在「保存中」），且 `if (response)` 恒真（`StatusPageConfigResponse` 根本没有 success 字段），else 分支是死代码。
另外 `fetchData` 的 useCallback 依赖 `[t]`——**切换语言会重新拉配置并覆盖表单**，正在编辑的未保存内容被静默丢弃。

### L18. 前端：i18n 插值风格不一致导致主题提示渲染出花括号

`i18n/config.ts:18-19` 配置了自定义单花括号 `prefix:"{", suffix:"}"`，但 `en-US.ts:19` / `zh-CN.ts:19` 的 `themes.applied` 用了双花括号 `{{name}}`。全库仅这一对 key 风格漂移，实际会渲染出未替换的花括号。

## 三、架构层面问题

### A1. `db` 是全局 `any`，整个数据访问层零类型安全（最高杠杆）

`backend/src/config/db.ts:5` `let db: any;`——`tsconfig.json` 明明 `strict: true`，但所有 drizzle 查询都不受检查。直接后果：

- L3 的 `.where(字符串)` 和 `.count` 编译期查不出来；
- `repositories/monitor.ts` 里有 **10 处 `@ts-ignore`**（96/99/120/123/177/180/469/472/530/533）来硬塞 `headers`；
- 到处需要 `as Agent[]`、`as Metrics[]` 这类无根据断言（`repositories/agent.ts:761,765,831`）；
- 它还是模块级可变全局单例，repository 无法注入替身——这就是 `scripts/api-contracts.test.ts` 全是纯函数断言、**没有一条 DB 或 HTTP 层测试**的原因，也是 S1/S2/L3 长期未被发现的原因。

**这一项是解锁其余大部分问题的前提**：修掉它之后，L3、D1 这类问题会在编译期自动暴露。

### A2. 同一实体被定义 5 遍，且已实际漂移

Agent 实体存在于：`db/schema.ts:116`（drizzle 表）、`models/agent.ts:2-51`（手写 interface）、`api/schemas.ts:197-274`（zod 再写）、`frontend/src/types/agents.ts:5-48`（TS 再写）、`agent/pkg/model/collector.go`（Go struct）。

已确认的漂移：

| 位置 | 问题 |
|---|---|
| `frontend/src/types/monitors.ts:19` | 声明必填 `user_id`，后端根本没这字段（是 `created_by`） |
| 同上 `:22` | `active` 前端是 `number`，后端 `models/monitor.ts:13` 是 `boolean` |
| `models/status.ts:2-9` | StatusPageConfig 缺 `theme`，而 schema/repository/service 全都已有——过期的手写 model 仍在被 import |
| `models/notification.ts:2-63` | `enabled/is_default/on_down` 声明为 boolean，实际列是 int → 返回给前端的是 0/1 但类型标成 boolean，这正是代码里 20+ 处 `// 修复:` 注释的来源 |
| `models/db.ts:2-33` | 手写 D1/DO 类型，而 `@cloudflare/workers-types` 已在依赖里，只是 `tsconfig.json` 没配 `types` |

drizzle 的 `$inferSelect` 全仓库只用了 2 处（`repositories/agent.ts:81,499`）。这是 pnpm workspace 却没有 shared 包、没有 codegen 的直接代价；Go 侧靠注释人肉镜像，而**镜像注释已经烂了**（`agent/pkg/buffer/ring.go:8-10` 引用的 `MAX_SAMPLES_PER_AGENT` 常量早已改名为 `MAX_REPORT_SAMPLES`）。

### A3. Service 层返回 HTTP 状态码，API 层只做机械转发

所有 service 返回 `{success, message, status: 200|400|404|500}`，api 层清一色转发，产生 **20 处 `as any`**（`api/monitors.ts` 9 次、`users.ts` 6 次、`agents.ts` 5 次），因为 service 的 status 被推导成 `number` 而 Hono 要求字面量联合。

后果：HTTP 关注点泄漏进 service（jobs 调用时那些 status 字段就是垃圾）；api 层有 20 段逐字相同的响应包装。
更糟的是 `api/notifications.ts:259,306,352,550,596` **靠中文错误文案的子串匹配决定 HTTP 状态码**：`result.message?.includes("不存在") ? 404 : 500`——文案一改状态码就错。

**修法**：service 抛领域错误或返回 Result，api 层用统一 errorHandler 映射状态码。

### A4. `services` 与 `jobs` 循环依赖

`services/AgentService.ts:13` import 自 `jobs/agent-task`，而 `jobs/agent-task.ts:2-11` 又 import 自 `services`。这也解释了 L10 里 env 被传成 `{}`——层次已经乱到没人知道该传什么。通知编排应抽成独立 service，job 只做调度。

另外 `services/AgentService.ts:20-26` 从 `api/schemas` import 校验 schema 来推导入参类型，依赖方向倒置。

### A5. Repository 层承担鉴权与业务判断

- `repositories/monitor.ts:87-90` 把**授权判断写在 repository**（`if (userRole !== 'admin' && created_by !== userId) return null`），而 agent 侧的同类判断在 service（`AgentService.ts:1003-1009`）——同一概念两处实现、两个层次；
- `repositories/notification.ts:642-661` 的「资源级优先、回退全局」是纯业务规则；
- `repositories/agent.ts:266-335` 的分区分配 + 冲突重试是领域逻辑；
- `repositories/monitor.ts:511-514` 甚至返回 `{message: "没有提供要更新的字段"}` 这种业务错误对象，逼得 service 写 `"message" in updatedMonitor` 来判别。

同时 Service 层大量只是透传（`AgentService.ts:998,1011,1015`、`MonitorService.ts:23-25`、`NotificationService.ts:138-149,223-234,307-311`、整个 `SettingsService.ts`）——贫血层。

### A6. 前端没有数据层，每个页面手写一遍状态机

全站 10+ 处都是 `useState(loading/error/data)` + `useCallback(fetch)` + `usePolling` 的手写组合，没有 react-query/SWR。L15、L16、L17 三个 bug 全部源于此——每页各写各的，写错一个就是一个 bug。

`hooks/usePolling.ts` 本身质量不错（in-flight 去重、visibilitychange 补拉、StrictMode 处理），但它只解决「定时」，不解决缓存/去重/错误重置/竞态——等于自研了 react-query 的 5%，让每个页面自己补齐剩下的 95%。

### A7. 前端 API 层三种互相矛盾的错误契约

| 模式 | 位置 |
|---|---|
| 吞错返回 `{success:false, message:"硬编码中文"}` | `api/agents.ts:10-25,70-98`、`api/monitors.ts:100-134`、`api/notifications.ts` 全文件 |
| 直接 throw 交给页面 catch | `api/monitors.ts:12-97`、`api/status.ts`、`api/users.ts`、`api/auth.ts` |
| 伪造成功（无条件 `success:true`） | `api/agents.ts:27-33` |

`agents.ts` 一个文件内就混用了三种。后果是页面既要 try/catch 又要判 `response.success`，且模式 A 的**硬编码中文**被 `toast.error(response.message)` 直接展示给英文用户。

### A8. 单个全局 Durable Object 承载所有租户

`services/BroadcastService.ts:52` 和 `api/ws.ts:112` 都用 `idFromName("global")`——全站所有 agent 的推送和所有用户的 WebSocket 都挤在**一个单线程 DO 实例**里。`durable/MetricsBroadcaster.ts:353-392` 对每个 socket 做 deserialize + Set 构造 + filter + stringify，开销是「连接数 × 更新数」。且跨租户可见性完全依赖 Worker 侧计算的 `X-Allowed-Agent-Ids` 头，DO 无条件信任。

应按 userId 分片（`idFromName(String(userId))`）。

### A9. 监控吞吐被硬约束在 50 个监控项

`wrangler.toml` 的 `crons = ["* * * * *"]` + `MONITOR_CHECK_BATCH_SIZE = "10"` = 每分钟最多检查 10 个 = 600/小时；配合 `MIN_MONITOR_INTERVAL_SECONDS = 300`（每监控 5 分钟一次），系统容量上限是 **50 个监控项**。超过之后 `next_check_at` 队列持续积压、实际间隔无限拉长，而**没有任何告警**能发现这件事。

### A10. Docker 部署路径是把 `wrangler dev` 当生产运行时

`Dockerfile:32` → `pnpm run preview` → `backend` 的 `"dev": "wrangler dev --test-scheduled"`。生产容器跑的是 miniflare 开发模拟器，D1 是 `.wrangler` 目录下的本地 SQLite，cron 靠容器 crontab 每分钟 curl 测试端点 `/__scheduled`。叠加 S5 → 每次容器重启全员登出。
且 `Dockerfile:2` 用 node:20，而 `deploy.yml:41-42` 自己注明「Wrangler 4 需要 Node.js 22 或更高」——两条部署链路的运行时要求互相矛盾。

### A11. 迁移 DDL 跑在请求路径上

`index.ts:100-107` → `db/migration.ts:51-93`：冷 isolate 的第一个 HTTP 请求执行 `CREATE TABLE`/`ALTER TABLE`，逐条 statement 无原子性；非幂等 ALTER 执行到一半失败 → migrations 表不记录 → 每次请求重放 → duplicate column → 永久 500。
并发方面只有 per-isolate 的 `dbInitialized` 布尔（且是 `await` 之后才置位的 TOCTOU），多 isolate 冷启动可并发跑同一迁移；`scheduled()` 入口完全不检查迁移。
迁移里还夹带数据修复（`0006` 全表 UPDATE 回填、`0007` 先 DELETE 去重再建唯一索引），大表时由首个用户请求承担。

应改走 `wrangler d1 migrations apply`。

### A12. theme-shim：565 行的 Radix Themes 兼容垫片，双 UI 体系并存

`frontend/src/components/ui/theme-shim.tsx` 在运行时把 Radix Themes 风格 props 翻译成 Tailwind 类名 + inline style，含手写的 5 断点 × 8 值映射巨表。同一元素的样式来源有三处（shim class、inline style、外部 className），排查样式必须读 shim 源码。`Theme` 组件是空壳直通；`IconButton` 的 `variant="soft"` 没有对应分支，而调用方大量传这个值（实际是无效 prop）。

这是从 Radix Themes 迁往 shadcn/Tailwind 的过渡层，但迁移停在中间态——几乎每个页面仍以 shim 为主要布局原语，新代码继续以废弃 API 风格书写。需要定方向：要么完成迁移删掉它，要么承认它是设计系统并补齐 variant。

### R6. 数据库层的性能冗余

- **批量排序用 N 条独立 UPDATE**：`repositories/monitor.ts:142-148` 用 `Promise.all` 发 N 条，而 schema 允许最多 1000 个 id → 1000 条并发 D1 语句，极易触发限流。`repositories/status.ts:142,164` 已经会用 `db.batch()`，说明能力具备只是没用。
