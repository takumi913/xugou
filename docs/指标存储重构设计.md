# 指标存储重构设计

> 状态：待实施。线上探针已停止，D1 已清理至 3.3 MB，可直接按本设计重构后发版。

## 1. 背景与目标

2026-08-12 线上 D1 写满（`D1_ERROR: Exceeded maximum DB size`），整站写入冻结 7 天。
根因是探针 1 秒采集配合 30 天原始样本保留期，单机产生 139.5 MB/天，
36 小时写入 130,040 行 / 210 MB。

**目标：保持 1 秒采集，在 500 MB D1 内支撑 30–40 台机器，1 秒精度至少可回溯 24 小时。**

### 1.1 容量预算（已按 T1 实测校准）

数据来源：`go test ./pkg/metricblock/ -run TestCompressionRatio`，
基于线上真实样本 + 随机游走抖动（刻意比正弦波更毛糙，避免高估压缩比）。

| 分辨率 | 序列 | 保留 | 单机/天 | 40 台占用 |
| --- | --- | --- | --- | --- |
| 1 秒 | 全部 33 序列 | 预算 250 MB → **41.5 小时** | 3.62 MB | 250 MB |
| 1 分钟 | 33 序列 × avg/min/max | 7 天 | 36.1 KB | 9.9 MB |
| 其它（监控/状态页/索引/余量） | | | | ~60 MB |
| **合计** | | | | **~320 MB（64%）** |

实测关键数：**每样本 43.9 B，压缩比 36.8×**，满 60 点的 1 分钟聚合块 1,541 B。

预算档位对照：

| 1 秒层预算 | 覆盖时长 | 库总占用 |
| --- | --- | --- |
| 150 MB | 24.9 小时 | 220 MB（44%） |
| **250 MB** | **41.5 小时** | **320 MB（64%）** |
| 300 MB | 49.8 小时 | 370 MB（74%） |

> **相对初版设计的修正**：初版按模拟压缩比 132× 估算，称 150 MB 可覆盖 48 小时——
> 该数字与同表"40 台占用 137 MB"自相矛盾（137 MB 本就只是一天的量）。
> 实测压缩比 36.8×，150 MB 实际只够 24.9 小时，紧贴底线无余量，故预算上调到 250 MB。
> 另一方面 1 分钟层实测仅 9.9 MB，比初版估算的 48 MB 便宜 5 倍，正好补上这笔预算。

规模变化时优雅降级（250 MB 预算下）：60 台 → 约 27.7 小时，80 台 → 约 20.8 小时。
80 台跌破 24 小时底线，届时把预算提到 300 MB 即可（覆盖 24.9 小时，库占用 74%）。

### 1.2 为什么能省下来

单条样本 1,595 字节中 **82.3% 是每秒重复一遍的固定开销**：

```
JSON 键名          854 B  53.5%
静态元数据         275 B  17.2%   (CPU 型号 / 设备名 / 挂载点 / fs_type / ping 目标)
可推导的冗余字段   143 B   9.0%   (usage_rate / free / rx_speed 都能算出来)
ISO 时间戳          41 B
真正每秒变化的量   33 个
```

不改采集频率，只改存储形态：**一秒一行 JSON → 一分钟一行压缩块**。
列式排布 + 定点化 + delta + gzip，模拟压缩比 132×，按 **40 B/样本** 保守规划。

同时行写入量从 345 万行/天降到 5.8 万行/天（60×）。

## 2. 总体数据流

```
Agent (1 Hz 采集，不变)
  │
  ├─ collectSample ──> spool.Add()          每样本一个文件（崩溃恢复语义不变）
  │                     │
  │                     └─> liveClient      实时 WebSocket 推送（完全不动）
  │
  └─ runReportLoop (60s)
       └─ spool.Next()  ──> 按分钟桶分组，只取【已完整】的桶
            ├─ metricblock.Encode(res=1)   每个完整分钟桶 → 一个 1 秒块
            └─ 内存滚动聚合                当前小时的 1 分钟点 → 一个 1 分钟块
                 │
                 ▼
            AgentReport{ blocks: [...] }  ──HTTP──> Worker
                                                     │
                                          ┌──────────┴──────────┐
                                          ▼                     ▼
                              agent_metric_blocks      agent_current_metrics
                              (upsert，幂等)            (最新快照，单行/agent)
```

关键：**编码器只在 Go，解码器只在 TS**。生产链路上服务端不需要编码器，Agent 不需要解码器。

## 3. 块格式规格（codec v1）

所有多字节整数一律 **小端**。

```
Block ::= Header || DimHeader || SeriesDescriptors || Payload
```

### 3.1 Header（固定 32 字节）

| 偏移 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
> **实现修正**：初版写"固定 28 字节"有误。`swap_total` 位于偏移 24 且占 8 字节，
> 头部实际为 **32 字节**（`HeaderSize = 32`）。

| 0 | u8 | magic | 固定 `0xB1` |
| 1 | u8 | codec_version | 固定 `1` |
| 2 | u8 | interval_seconds | `1` 或 `60` |
| 3 | u8 | flags | 见下 |
| 4 | u8 | aggregate_count | `1`（res=1）或 `3`（res=60，顺序 avg/min/max） |
| 5 | u8 | reserved | 写 `0`，读时忽略 |
| 6 | u16 | series_count | |
| 8 | u16 | slot_count | 时间槽数，恒为 60；决定 presence bitmap 宽度 |
| 10 | u16 | reserved2 | 写 `0` |
| 12 | u32 | bucket_start | epoch 秒，UTC |
| 16 | u64 | memory_total | 静态量，随块携带 |
| 24 | u64 | swap_total | 无 swap 时写 `0` |

`flags`：

- `bit0 (0x01)` — Payload 经 gzip 压缩
- `bit1 (0x02)` — Payload 含 presence bitmap
- 其余位保留，写 0

> **`slot_count` 与 `point_count` 是两个不同的量，勿混用**（实现期发现，初版设计遗漏）：
>
> - 块头里的 `slot_count` 恒为 60，表示时间槽总数，决定 presence bitmap 的宽度
> - 上报体与 DB 列里的 `point_count` 是**实际存在的槽数**，用于 §5.2 upsert 的单调守卫
>
> 若两者都写 60，`excluded.point_count >= existing.point_count` 这条守卫将永远成立，
> Agent 重启后重传的半小时块就会覆盖掉更完整的既有块。两种分辨率的桶跨度：
> `resolution=1` 为 1 分钟（60 × 1 秒），`resolution=60` 为 1 小时（60 × 1 分钟）。

### 3.2 DimHeader（变长，自描述）

```
u8  disk_count
  disk_count × { u8 name_len || name(utf8, mount_point) || u64 total }
u8  net_count
  net_count  × { u8 name_len || name(utf8, interface) }
u8  ping_count
  ping_count × { u8 name_len || name(utf8, key 如 ct/cu/cm/bd) }
```

`name_len` 上限 255，超长截断。`disk_count` / `net_count` / `ping_count` 上限 64，
超出部分丢弃（与现有 `collector.maxMetricItems = 128` 的行为对齐，取更保守值）。

**设计取舍**：设备名等静态元数据写进块自身而不是外部维度表，每块多约 275 B
（摊到 60 个样本约 4.6 B/样本），换来块可以脱离任何外部状态独立解码，
并省掉「维度表版本化 + 磁盘增减时的版本迁移」整套机制。

### 3.3 SeriesDescriptors（`series_count` × 4 字节）

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| u16 | series_id | 见 §4 注册表 |
| u8 | encoding | `0`=delta-varint `1`=delta-of-delta `2`=raw |
| u8 | scale_pow10 | `stored_int = round(value × 10^scale)` |

描述符按 `series_id` 升序排列，Payload 中各序列的数据段顺序与此一致。

### 3.4 Payload

gzip 前的字节流，按描述符顺序逐序列拼接。每个序列：

```
for agg in 0 .. aggregate_count-1:
    [presence bitmap]  仅当 flags.bit1；ceil(point_count/8) 字节，
                       LSB-first，bit i = 第 i 个点存在
    values             仅编码 present 的点，zigzag varint
```

`values` 的编码规则：

- `encoding=0`（delta-varint）：首个 present 值写绝对值，其后每个写与**前一个 present 值**的差
- `encoding=1`（delta-of-delta）：首值写绝对值，第二值写一阶差，其后写二阶差。
  用于单调递增的网络计数器
- `encoding=2`（raw）：每个点独立写绝对值。用于布尔量

zigzag：`encode(n) = n < 0 ? -2n-1 : 2n`，再按 7 位一组的 varint 输出（LSB-first，
高位续位标志）。

### 3.5 缺失值

用 presence bitmap，**不用哨兵值**。`PingResult.LatencyMs` 丢包时真实取值就是 `-1`，
用哨兵必然撞车。

若某块所有序列所有点都存在，则不置 `flags.bit1`，省掉全部 bitmap 开销（常态）。

### 3.6 边界与校验

解码器必须校验并在不满足时返回错误（不得 panic / 静默截断）：

- `magic == 0xB1 && codec_version == 1`
- `interval_seconds ∈ {1, 60}`
- `aggregate_count ∈ {1, 3}`
- `series_count ≤ 512`、`point_count ≤ 3600`
- 解压后 Payload 长度与按描述符推算的期望长度一致
- `series_id` 落在 §4 定义的合法区间
- 解压上限 1 MB，超出直接拒绝（防 zip bomb）

两端各维护一份常量表，**必须逐字节一致**。

### 4.1 标量（1–99）

| id | 来源字段 | scale | encoding |
| --- | --- | --- | --- |
| 1 | `cpu.usage` | 2 | 0 |
| 2 | `memory.used` | 0 | 0 |
| 3 | `memory.free` | 0 | 0 |
| 4 | `load.load1` | 2 | 0 |
| 5 | `load.load5` | 2 | 0 |
| 6 | `load.load15` | 2 | 0 |
| 7 | `swap.used` | 0 | 0 |
| 8 | `process_count` | 0 | 0 |
| 9 | `tcp_connections` | 0 | 0 |
| 10 | `udp_connections` | 0 | 0 |
| 11 | `ipv4_reachable` | 0 | 2 |
| 12 | `ipv6_reachable` | 0 | 2 |

### 4.2 按实例（slot 由 DimHeader 顺序决定，0-based）

| 区间 | 公式 | 来源字段 | scale | encoding |
| --- | --- | --- | --- | --- |
| 100–163 | `100 + slot` | `disks[slot].used` | 0 | 0 |
| 200–455 | `200 + slot*4 + 0` | `network[slot].bytes_sent` | 0 | 1 |
| | `200 + slot*4 + 1` | `network[slot].bytes_recv` | 0 | 1 |
| | `200 + slot*4 + 2` | `network[slot].packets_sent` | 0 | 1 |
| | `200 + slot*4 + 3` | `network[slot].packets_recv` | 0 | 1 |
| 500–627 | `500 + slot*2 + 0` | `ping[slot].latency_ms` | 3 | 0 |
| | `500 + slot*2 + 1` | `ping[slot].loss`（0/1） | 0 | 2 |

### 4.3 不入块的字段

以下字段**不写进块**，因为可由块内数据推导或属于静态元数据：

- `memory.usage_rate`、`swap.usage_rate`、`disks[].usage_rate`、`disks[].free`
  → 由 `used` 与 DimHeader / Header 里的 `total` 算出
- `network_rx_speed` / `network_tx_speed` → 由相邻两点的 `bytes_recv` / `bytes_sent` 差分算出
- `cpu.cores`、`cpu.model_name`、`disks[].device`、`disks[].fs_type`、`ping[].target`
  → 静态，写入 `agent_current_metrics` 与 `agent_nodes`，随最新快照更新

`ping[].target` 不进 DimHeader（DimHeader 只放 key 如 `ct`/`cu`），target 是配置项，
放 `agent_nodes`。

## 5. 数据库

### 5.1 新表

```sql
CREATE TABLE agent_metric_blocks (
  id           INTEGER PRIMARY KEY,
  agent_id     INTEGER NOT NULL REFERENCES agents(id) ON DELETE CASCADE,
  resolution   INTEGER NOT NULL,  -- 1 = 1秒块, 60 = 1分钟块
  bucket_start INTEGER NOT NULL,  -- epoch 秒；res=1 为分钟起点，res=60 为小时起点
  point_count  INTEGER NOT NULL,  -- 实际存在的槽数（≠ 块头里恒为 60 的 slot_count）
  codec        INTEGER NOT NULL,
  byte_size    INTEGER NOT NULL,  -- length(data)，避免 GC 时反复算
  data         BLOB NOT NULL
);

CREATE UNIQUE INDEX agent_metric_blocks_key_idx
  ON agent_metric_blocks (agent_id, resolution, bucket_start);
CREATE INDEX agent_metric_blocks_gc_idx
  ON agent_metric_blocks (resolution, bucket_start);
```

> **实现修正：不要用 `WITHOUT ROWID`**（初版设计的建议是错的）。
>
> SQLite 官方指出，`WITHOUT ROWID` 只适合行较小的表，经验法则是**平均行大小应低于
> 页面的 1/20**。页面 4096 B 对应约 205 B，而本表的块行实测约 2.6 KB，
> 用 `WITHOUT ROWID` 会把大 payload 直接塞进索引 B-tree 并产生 overflow 链，
> 反而更慢。
>
> 改用普通 rowid 表后：唯一索引承担主键语义（`ON CONFLICT` 照常工作），
> rowid 还让 GC 能用 `WHERE rowid IN (...)` 的简单批量删除写法，
> 初版为规避 `WITHOUT ROWID` 而设计的主键三元组删除也就不需要了。

### 5.2 写入（幂等 + 单调）

```sql
INSERT INTO agent_metric_blocks
  (agent_id, resolution, bucket_start, point_count, codec, byte_size, data)
VALUES (?, ?, ?, ?, ?, ?, ?)
ON CONFLICT(agent_id, resolution, bucket_start) DO UPDATE SET
  point_count = excluded.point_count,
  byte_size   = excluded.byte_size,
  data        = excluded.data
WHERE excluded.point_count >= agent_metric_blocks.point_count;
```

`WHERE` 子句保证单调：Agent 重启后重传一个更短的 1 分钟块不会覆盖更完整的既有块。
重传相同块是无副作用的幂等操作，**因此不再需要 `agent_reports` 的去重表和状态机**。

### 5.3 被替换掉的表

```
agent_report_samples       ┐
agent_reports              │
agent_metric_rollups       ├──→  agent_metric_blocks
agent_metrics_history      │
agent_metrics_history_old  │
agent_metrics_24h          │
agent_latest_metrics       ┘
agent_current_metrics      ──→  保留（仪表盘最新快照 + 静态元数据）
```

**8 张表 → 2 张。**

## 6. Agent 侧改动

### 6.1 新包 `agent/pkg/metricblock/`

```go
// Encode 把同一分钟桶的样本编码成 1 秒块。samples 必须按时间升序且属于同一桶。
func Encode(bucketStart int64, interval int, samples []*model.AgentReportSample) ([]byte, error)

// EncodeRollup 把当前小时累积的 1 分钟聚合点编码成 1 分钟块。
func EncodeRollup(hourStart int64, points []*MinutePoint) ([]byte, error)

// MinutePoint 是一分钟内所有序列的 avg/min/max。
type MinutePoint struct {
    MinuteStart int64
    Dims        Dims                 // 该分钟的磁盘/网卡/ping 拓扑
    Values      map[uint16][3]float64 // series_id -> {avg, min, max}
    Present     map[uint16]bool
}

// Aggregate 从一分钟的原始样本算出 MinutePoint。
func Aggregate(minuteStart int64, samples []*model.AgentReportSample) *MinutePoint
```

**注意**：`Aggregate` 对单调计数器（`encoding=1` 的网络计数器）取 **last** 而非 avg，
否则速率无法从相邻分钟差分还原。avg/min/max 三元组里对这类序列写 `{last, last, last}`。

### 6.2 `agent/pkg/spool/spool.go`

`Next()` 改为按分钟桶分组，**只返回已完整的桶**（`bucketStart + 60 <= now`），
当前分钟的样本留在 spool 里等下一轮。

其余（每样本一文件、inflight、`Ack`、`enforceBounds`）**完全不动**——
崩溃恢复语义是现有实现的强项，不要动它。

### 6.3 `agent/pkg/model/collector.go`

（实时 WebSocket 链路完全不动）：

### 6.4 聚合累积器的归属（实现期调整）

初版设计把当前小时的 `[]*MinutePoint` 环形缓冲放在 `start.go` 的 `runReportLoop` 里。
**实现时改放到 `spool.Store`**，原因是：`Next()` 在返回前就把上报体固化进了 inflight
manifest，若由 `start.go` 在拿到 report 之后再追加聚合块，持久化的副本与实际发送的
内容就不一致，重启后重发的批次会缺聚合块。累积器与样本同属 spool，放一起更内聚。

`Next()` 的完整流程：

1. `collectBuckets` 按分钟桶归拢，**只取已完整的桶**（`bucketStart + 60 <= now`）
2. 逐桶试探压缩体积，超过上限就停在桶边界
3. 对入选的桶调 `metricblock.Encode` → 1 秒块
4. 对入选的桶调 `metricblock.Aggregate` 并入 `Store.rollupPoints`
5. `buildRollupBlocks` 为累积器里每个小时生成聚合块，随后只保留最新小时的点

进程重启丢失累积器，导致重传更短的聚合块——由 §5.2 的 `WHERE` 子句兜住，
Agent 侧不需要持久化。

> **实现期发现的数据丢失 bug（已修）**：桶必须是**原子单位**。
>
> 初版按样本数硬性截断组批，会出现「第二个桶只发 40 点 → `Ack` 删掉这 40 条
> → 剩余 20 条下一轮组成同一桶的 20 点块 → 服务端单调守卫拒绝（20 < 40）
> → 这 20 秒永久丢失」。
>
> 修法：`maxSamples` 上限只在**开启新桶时**检查，绝不半途截断。
> 代价是单批最多超出上限一个桶（1 Hz 下 ≤ 60 条），可接受。
> 回归测试见 `TestBucketsAreAtomic`。

### 6.5 ping 频率 —— 无需改动（原判断有误，已更正）

初版设计担心「每个样本都带四路 TCP 拨测 → 40 台 × 1 Hz = 每秒 160 次连接会被封 IP」。
**读代码后确认该担心不成立**：`agent/pkg/collector/netprobe.go:16` 已有

```go
// probeInterval 拨测独立周期：结果缓存 30 秒，采集频率再高也不会放大拨测开销
probeInterval = 30 * time.Second
```

`netProber.current()` 返回缓存快照并在后台刷新（`refreshing` 标志防并发），
生产数据里每秒样本都带 ping 值只是**同一份缓存被复制进每个样本**，实际拨测仍是 30 秒一次。
`inventorySnapshot`（磁盘/CPU 枚举）同样有 30 秒缓存。

对块编码而言，重复的相同值 delta 后全为 0，每点约 1 字节，成本可忽略，
因此**也不需要把它们标记为 missing**。原 T7 任务取消。

```ts
  point_count:  z.number().int().min(1).max(3600),
  codec:        z.literal(1),
  data:         z.string().max(262144), // base64，约 192 KB 原始
}).strict();

// protocol_version 升到 5，samples -> blocks
blocks: z.array(agentReportBlockSchema).min(1).max(120),
```

### 7.3 读路径

按窗口跨度选分辨率，返回点数上限 2000：

| 窗口 | 分辨率 | 说明 |
| --- | --- | --- |
| ≤ 25 分钟 | `resolution = 1` | 真 1 秒精度 |
| > 25 分钟 | `resolution = 60` | 7 天图 = 168 块 |

依据：图表宽度约 1,500 px，任何超过约 25 分钟的窗口本来就要降采样。

共享查询层 `metricblock/query.ts`：

- `queryAgentSamples` — 单 agent
- `queryAgentSamplesBatch` — 多 agent 一次 D1 往返（状态页要同时渲染多台机器，
  逐个查会把往返次数放大到 agent 数量）
- `downsample` — 等距抽样并**始终保留最后一个点**（最新数据点不能因步长对不齐被丢掉）

已改造：

- `D1StatusRepository.buildPublicAgentMetricPublications` → 直读 1 分钟层（窗口固定
  24 小时），降采样到 288 点。rollup/raw 二选一的 fallback 分支整个删除
- `D1LegacyAgentFacade.queryLegacyAgentMetrics` → 按窗口选分辨率，降采样到 160 点

**单个坏块不会让整张图空掉**：解码失败只跳过该块并记结构化日志
（`METRIC_BLOCK_DECODE_FAILED`），其余照常返回。

> **顺带清掉的死代码**：`queryLegacyAgentMetrics` 里
> `for (const table of contractMode ? [] : await [])` 两个分支都是空数组，
> 循环体从未执行，`legacyRows` 恒为空 —— 与 `prepareAgentMetricRollupRebuild`
> 同类的问题。随本次改造一并移除的还有 `toRollupMetric`、`toHistoryMetric`、

### 7.4 保留策略

`backend/src/jobs/index.ts` 的 `cleanupOldRecords` 中，agent 相关的四个
`*_RETENTION_DAYS` 全部删除，替换为：

```sql
-- 规则 1：每个 cron tick 执行，走 gc 索引的范围删除，成本低
DELETE FROM agent_metric_blocks WHERE bucket_start < :now - 7*86400;

-- 规则 2：每小时执行一次。先判断是否超预算
SELECT COUNT(*) AS n, SUM(byte_size) AS bytes
FROM agent_metric_blocks WHERE resolution = 1;

-- 超预算则删最旧的一批
DELETE FROM agent_metric_blocks
WHERE rowid IN (
  SELECT rowid FROM agent_metric_blocks
  WHERE resolution = 1 ORDER BY bucket_start ASC LIMIT 500
);
```

新增环境变量：

```toml
AGENT_BLOCK_HOT_BUDGET_BYTES = "262144000"   # 250 MB，resolution=1 预算（实测覆盖 41.5 小时）
AGENT_BLOCK_MAX_AGE_DAYS     = "7"
AGENT_BLOCK_GC_BATCH         = "500"
```

**这条规则的价值在于不需要预测压缩比。** 压得好就多存几小时，压得差就少存几小时，
但永远不会撑爆。估算错误的后果从"整站瘫痪 7 天"降级成"历史短一点"。

### 7.5 调度器可靠性（独立 bug，必须一并修）

**`backend/src/jobs/index.ts:78-88`**：当前是

```
await monitorTask.scheduled(...)   // 库满 → agent-task.ts:79 的 DB.batch 抛异常
await agentTask.scheduled(...)
if (hour === 0 && minute === 30) await cleanupOldRecords(env)   // 永远走不到
```

「库满 → 前置任务抛异常 → 清理永不执行 → 库永远满」的自锁循环，
是这次躺 7 天没自愈的直接原因。修法：

1. `monitorTask.scheduled` / `agentTask.scheduled` 各自包 try/catch 并记结构化日志
2. `cleanupOldRecords` 提到最前面执行
3. 移除单分钟执行窗口 —— `jobs/index.ts:86` 的 `hour===0 && minute===30` 与
   `monitor-task.ts` 的 `hour===0 && minute===5` 都改为在 `settings` 表存
   `last_run_at`，超过间隔就跑。Cloudflare cron 不保证准点触发，漏一次就整天不清理
